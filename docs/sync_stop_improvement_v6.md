# [최종 보고서 v6] 하드웨어 주기 동기화 및 실시간성 보장 로직

본 문서는 `DrumRobot2`의 **5ms 하드웨어 전송 주기**를 안정적으로 유지하기 위한 **'마디 단위 벌크 계산(Bulk Calculation)'**과 **'2마디 선점 적재'** 전략을 상세히 설명합니다.

---

## 1. 하드웨어의 요구조건: 5ms의 벽
*   **물리 주기**: `CanManager`는 5ms(또는 1ms)마다 꼬박꼬박 모터에 명령을 실어 보내야 합니다. (200Hz ~ 1000Hz 전송)
*   **위험 요소**: 만약 특정 시점에 보낼 데이터가 없다면, 모터 제어 신호에 지터(Jitter)가 발생하거나 통신 오류로 이어져 연주가 끊기게 됩니다.

---

## 2. 소프트웨어의 해결책: 벌크 생산 (Bulk Production)
소프트웨어는 5ms마다 하나씩 계산하는 방식이 아니라, **'마디(Measure)'라는 거대한 데이터 뭉치**를 한꺼번에 계산합니다.

*   **소비 시간**: 한 마디 연주에 약 **2,000ms (2초)**가 소요된다고 가정 (120 BPM 기준).
*   **생산 시간**: C++ 기반 IK Solver가 한 마디 분량(수백 개의 점)을 계산하는 데 걸리는 시간은 약 **50ms** 내외.
*   **결론**: **"2초 동안 쏠 데이터를 만드는 데 단 0.05초면 충분"**합니다. 즉, 생산 속도가 소비 속도보다 약 40배 이상 빠르기 때문에 이론적으로는 밀릴 수가 없습니다.

---

## 3. '2마디 선점 적재'가 필요한 진짜 이유
이론적으로는 생산이 훨씬 빠름에도 불구하고, 왜 **Full-Start(2개 채우고 시작)**가 필요한가? 그것은 **'초기 레이턴시(Initial Latency)'** 때문입니다.

1.  **시작 시점의 시차**: 연주 시작 버튼을 누른 '찰나'의 5ms 주기에 데이터를 쏘려면, 그전에 이미 계산이 끝나 있어야 합니다. 시작과 동시에 계산을 하면 첫 박에서 50ms의 지연이 발생할 수 있습니다.
2.  **OS 스케줄링 방어**: 리눅스는 실시간 OS(RTOS)가 아니므로, 때때로 다른 작업 때문에 계산 스레드가 수십 ms 밀릴 수 있습니다.
3.  **안전 자산 확보**: 미리 **2마디(약 4초치)**를 채워두면, 설령 운영체제나 네트워크 문제로 계산이 1~2초간 지연되더라도 **5ms 주기의 모터 전송은 선반에 남은 2번 마디 덕분에 끊기지 않고 유지**됩니다.

---

## 4. 제어 시퀀스 요약: 5ms 주기를 지키는 법

| 단계 | 생산자 (PathManager) | 소비자 (CanManager) | 비고 |
| :--- | :--- | :--- | :--- |
| **1. 시작 전** | 1번, 2번 마디 벌크 계산 (50ms+50ms) | 대기 (Wait) | **안전 버퍼 확보** |
| **2. 연주 시작** | 2개가 찼으므로 대기 (Sleep) | 5ms 주기로 1번 마디 전송 시작 | **첫 박 지연 없음** |
| **3. 연주 중** | 1번이 소비되면 즉시 3번 계산 시작 | 2번 마디 대기분 덕분에 5ms 주기 유지 | **끊김 없는 연주** |
| **4. 정지 시** | 마지막 마디에 감속 로직 적용 | 남은 데이터를 모두 쏘며 부드럽게 종료 | **인간형 마무리** |

---

## 5. 결론: 실시간성 보장 전략
`DrumRobot2`는 **"5ms마다 점 하나를 쏘는 촘촘함"**과 **"2초치를 한꺼번에 계산하는 듬직함"**을 **2마디 완충 버퍼**로 연결했습니다. 이를 통해 소프트웨어의 계산 부하와 상관없이 하드웨어의 물리적 주기를 완벽하게 보장하며, 동시에 사용자가 의도한 "서서히 멈추는" 예술적 제어까지 가능하게 되었습니다.
