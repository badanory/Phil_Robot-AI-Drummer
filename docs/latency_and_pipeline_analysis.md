# [심층 분석 보고서] 제어 파이프라인의 구조적 딜레이 및 동기화 충돌 이슈

본 문서는 `DrumRobot2`의 궤적 생성 단위에 대한 오해를 바로잡고, 이로 인해 발생하는 **5마디(약 12초)의 제어 지연(Latency)** 및 **명령어 간 충돌(Stop vs Modifier)** 문제를 분석합니다.

---

## 1. 팩트 체크: '1줄'인가 '1마디'인가?

시스템의 궤적 생성 단위인 `lineOfScore`는 악보 텍스트 파일의 한 줄(0.6초)이 아니라, **2.4초 분량의 데이터 뭉치(1마디)**를 의미합니다.

*   **원인**: `readMeasure` 함수는 `getline`으로 파일을 읽으며, 누적 시간이 2.4초(`measureThreshold`)가 될 때까지 **소모적으로(Non-overlapping)** 읽어 들입니다.
*   **결과**: 한 줄씩 겹치면서 이동하는 슬라이딩 윈도우가 아니라, **4줄씩 통째로 넘기는 블록(Block) 단위 이동**입니다.
*   `preCreatedLine = 3`은 3줄(1.8초)이 아니라 **3마디(7.2초)**의 대기를 의미합니다.

---

## 2. 전체 제어 파이프라인 타임라인 (Double Latency)

텍스트 파일의 명령이 실제 로봇 모터의 움직임으로 나타나기까지의 과정입니다.

1.  **[텍스트 파싱 및 Modifier 적용]**: 텍스트 읽기 (맨 앞단)
2.  **[Task Space 큐]**: 미래 궤적 참고를 위해 **3마디(7.2초)** 대기 (`lineOfScore > 3` 규칙)
3.  **[IK 연산 및 Stop 꼬리표 부착]**: 관절 각도 계산 (중간단)
4.  **[Joint Space 큐 (모터 버퍼)]**: 안정성을 위해 **2마디(4.8초)** 대기 (`measure_count = 2` 규칙)
5.  **[로봇 연주]**: 실제 동작 (맨 끝단)

**👉 총 딜레이**: 텍스트에 적힌 악보나 Modifier가 로봇에 나타나려면 **3마디 + 2마디 = 총 5마디(약 12초)**의 시간이 필요합니다.

---

## 3. 치명적 버그: Stop과 Modifier의 적용 시점 불일치

사용자가 "느리게 멈춰라(Modifier + Graceful Stop)" 명령을 내렸을 때 발생하는 모순입니다.

*   **Modifier("느리게")**: 파이프라인 1번 단계에서 적용. 로봇에 도달하기까지 **12초** 소요.
*   **Stop("정지")**: 파이프라인 3번 단계에서 꼬리표 부착. 모터 버퍼만 통과하면 되므로 **4.8초** 소요.
*   **충돌 현상**: 로봇은 느려지라는 명령(12초 뒤 도착 예정)을 아직 받지 못한 상태에서, 정지하라는 명령(4.8초 만에 도착)을 먼저 받아버립니다. 결국 **감속 없는 원래 속도로 치다가 급정거**하게 됩니다.

---

## 4. 해결 방향 제안

의도하신 "서서히 멈추는 자연스러운 마무리"를 구현하려면 파이프라인의 딜레이를 축소하고 동기화해야 합니다.

1.  **소프트웨어 딜레이 축소**: `preCreatedLine`을 3에서 **1**로 변경하여, Task Space 대기를 1마디(2.4초)로 대폭 줄입니다.
2.  **명령어 적용 시점 일치**: Stop 플래그(`is_graceful_stopping`)를 IK 연산 단계가 아닌, 텍스트를 읽는 단계(`readMeasure`)와 연동하여 Modifier와 같은 속도로 큐를 통과하도록 수정해야 합니다.

본 분석을 바탕으로 로직 수정을 진행하면, 빠릿빠릿한 반응성과 우아한 마무리 제어를 동시에 달성할 수 있습니다.
